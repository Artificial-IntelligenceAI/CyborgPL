# Likely Updates

A running note of things that have come up as likely next steps or known gaps while building CyborgPL — not a committed roadmap, not a timeline, just an honest snapshot of what's been deferred so far and why. Language design items here are open questions for the project author to decide, not things an AI assistant should just go implement.

## Language design (not yet decided)

- Higher hyperoperator levels beyond `xxx` (tetration), if ever wanted.
- Whether real lexical block scoping (added for automatic bignum/str cleanup) should extend further.
- `numw`'s magnitude-word vocabulary is currently a fixed list (thousand/million/billion/trillion/quadrillion/quintillion) and only accepts one word after the number — no compound number words (`'one hundred thousand'`) and no expanding the list without a design decision.
- Whether `input:` should ever grow a built-in prompt (e.g. `input:str 'name' "Enter your name: ";`), or support `numw`/`bignum` — deliberately left out of the first version; right now you `print` your own prompt text first, and only `str`/`num` can be read.
- Whether `clock:` should ever support absolute/wall-clock time (not just elapsed-since-start), or a `bignum`/higher-precision variant for very short spans — deliberately left out of the first version; right now it's `num` only.
- Whether file writing should ever support append (only overwrite exists now), or whether `[to*(dest)*]`/`[from*(dest)*]` should extend to any other destination/source beyond a file.
- Whether `input:` reading from a file should ever support `numw`/`bignum`, or read just one line instead of the whole file (currently: whole file only, for both `str` and `num`) — deliberately left narrow for the first version, same pattern as stdin `input:`'s own initial scope.
- Arrays: nested arrays (`array:array:num`) are deliberately unsupported for the first version — `ElementType` can't itself be an array. (Array-typed function parameters and return values, and array-literal function arguments, already work — no design decision needed there, since `array:TYPE` is a `Type` like any other and every existing function-boundary/coercion path already handles it uniformly.) Not yet decided/started: a fixed-size array variant, removing/shrinking an array (only `append`, growing, exists), or any built-in way to iterate an array other than a manual `while` loop with `length`/indexing.
- `int` now supports `[precision:8/16/32/64]` (real hardware integer widths), with any width freely coercing to any other -- widening is always exact, narrowing is overflow-checked and crashes if the value doesn't actually fit (including immediately, mid-expression, if two ints of some width are combined and the result doesn't fit that width, even if the result is only ever printed and never stored). No explicit conversion bridge to/from `num`/`numw`/`bignum` (e.g. an explicit "round this num to an int" operator) — right now a fractional value can never reach an `int` at all by design, but there's also no sanctioned way to deliberately truncate/round a `num` into one either; would need its own design decision (truncate? round? crash on a fractional source?) if ever wanted.
- An `int` expression made entirely of literals (`(5000000000) x (5000000000)`, or a single out-of-range literal like `(200) [precision:8]`) that overflows is now caught at compile time instead of only crashing at runtime. Deliberately narrow: no constant propagation through variables (even ones assigned from a literal), no compile-time catch for division-by-a-literal-zero or a negative literal `xx` exponent (different, narrower failure modes than overflow), and `xxx` isn't constant-folded at all. Any of these could be extended later using the same `try_const_eval_int`/`ConstInt` machinery in typecheck.rs, but each would be its own design/scope decision, not an automatic given.

## Known implementation gaps

- `str` now has runtime construction via `stch` and real memory management (every `str` in a variable is its own `strdup`'d copy, freed at scope exit/reassignment/return, mirroring `bignum`). One remaining inefficiency: a `str` value stored somewhere always gets its own fresh copy even when the source was already an unshared temporary (a `stch` result, a str-returning call) — a redundant extra `strdup` in that case. `bignum` had the exact same redundant-copy pattern and it's now fixed (`compile_and_coerce` adopts a not-yet-consumed `bignum_temps` entry directly, skipping the copy, whenever its actual precision matches the target) — the same approach (an equivalent `str_temps` adoption check) would fix `str`'s version too, just not done yet.
- ~~Intermediate bignum binary-op results always compute at the default precision (256 bits) regardless of operand precision~~ -- fixed: intermediate results now widen to the larger of the two operands' own precisions (mirroring `num`'s "widen to the larger operand" behavior), computed via static AST inspection (`bignum_precision_of_expr` in codegen.rs) rather than a runtime GMP query, since a bignum's precision is fixed at construction and never changes afterward. Negation preserves the operand's own precision the same way; factorial still deliberately forces the default regardless of operand precision (unchanged, matching `num`/`int`'s own factorial convention).
- `mem2reg` now runs before object-file emission (promotes alloca/store/load into plain SSA values wherever safe). Nothing beyond it yet — inlining, dead code elimination, constant folding across function boundaries, etc. are all still deliberately deprioritized.
- The new type checker (`src/typecheck.rs`) only checks *shape* compatibility, not value validity — e.g. `var:bignum 'x' = (ref:var:str 'y');` type-checks fine (`str` is a valid bignum source, for numeric-literal text like `"3.14"`), but if `'y'` holds actual non-numeric text, that's still only caught at runtime (or not caught at all -- `bignum_set_str` on garbage input is undefined). Deliberately out of scope for a checker that mirrors codegen's existing coercion rules rather than adding new restrictions.
- `input:str 'x';` (stdin) strips the trailing newline; `input:str 'x' [from*(dest)*];` (a file) does not -- it hands back the file's exact, complete content. Not a bug (the file-source case was deliberately defined as "whole content, unmodified"), but worth knowing since it means a file written by `overwrite`/`print [to*...*]` (which always appends a newline) will read back with that newline still attached.
- Found while stress-testing arrays: any `build_alloca` placed inside a hand-built runtime loop's body block (as opposed to the function's entry block) is a genuine dynamic stack allocation on every iteration, since LLVM only reclaims it when the function returns — enough iterations (well under a million) segfaults the compiled program. Fixed for all the array codegen helpers via a new `entry_alloca` (see `AGENTS.md`); the same latent bug in `compile_tetration`/`compile_bignum_tetration`/`compile_factorial`/`compile_bignum_factorial` (pre-existing, unrelated to arrays) has since also been fixed the same way. Still unaudited: `Stmt::VarDecl`/`Stmt::Input`/`Stmt::Clock`'s own variable-slot allocas aren't hoisted either — harmless in every example so far (they always declare once outside a loop and reassign inside it), but a `var:` declaration written directly inside a `while` body, re-declaring each iteration, would hit the same bug. Not yet fixed since no real program has needed it.
- `int`'s literal grammar can't write the exact value `i64::MIN` (`-9223372036854775808`) directly -- its positive form (`9223372036854775808`) already exceeds `i64::MAX` on its own, before the negation that would produce it is even applied (the same `INT_MIN`-as-a-literal quirk most C-like languages have). Reachable via arithmetic instead (`-(9223372036854775807) - (1)`); every *other* literal in the full `i64` range parses exactly (parsed from the literal's original digit text, not the lexer's lossy `f64`, mirroring the fix `bignum`'s bare literals already needed).

## Bigger, not-yet-started ideas

- True arbitrary precision beyond what GMP's `mpf_t` offers, or a fixed-width 256-bit float type — discussed as a much larger undertaking, unstarted.

Nothing here is a promise. It's context for whoever — human or AI — picks this project up next.
