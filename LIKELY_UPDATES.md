# Likely Updates

A running note of things that have come up as likely next steps or known gaps while building CyborgPL — not a committed roadmap, not a timeline, just an honest snapshot of what's been deferred so far and why. Language design items here are open questions for the project author to decide, not things an AI assistant should just go implement.

## Language design (not yet decided)

- Higher hyperoperator levels beyond `xxx` (tetration), if ever wanted.
- Whether real lexical block scoping (added for automatic bignum/str cleanup) should extend further.
- `numw`'s magnitude-word vocabulary is currently a fixed list (thousand/million/billion/trillion/quadrillion/quintillion) and only accepts one word after the number — no compound number words (`'one hundred thousand'`) and no expanding the list without a design decision.
- Whether `input:` should ever grow a built-in prompt (e.g. `input:str 'name' "Enter your name: ";`), or support `numw`/`bignum` — deliberately left out of the first version; right now you `print` your own prompt text first, and only `str`/`num` can be read.
- Whether `clock:` should ever support absolute/wall-clock time (not just elapsed-since-start), or a `bignum`/higher-precision variant for very short spans — deliberately left out of the first version; right now it's `num` only.
- Whether file writing should ever support append (only overwrite exists now), or whether `[to*(dest)*]`/`[from*(dest)*]` should extend to any other destination/source beyond a file.
- Whether `input:` reading from a file should ever support `numw`/`bignum`, or read just one line instead of the whole file (currently: whole file only, for both `str` and `num`) — deliberately left narrow for the first version, same pattern as stdin `input:`'s own initial scope.
- Arrays: nested arrays (`array:array:num`) are deliberately unsupported for the first version — `ElementType` can't itself be an array. (Array-typed function parameters and return values, and array-literal function arguments, already work — no design decision needed there, since `array:TYPE` is a `Type` like any other and every existing function-boundary/coercion path already handles it uniformly.) Not yet decided/started: a fixed-size array variant, removing/shrinking an array (only `append`, growing, exists), or any built-in way to iterate an array other than a manual `while` loop with `length`/indexing.
- `int` now supports `[precision:8/16/32/64]` (real hardware integer widths), with any width freely coercing to any other -- widening is always exact, narrowing is overflow-checked and crashes if the value doesn't actually fit (including immediately, mid-expression, if two ints of some width are combined and the result doesn't fit that width, even if the result is only ever printed and never stored). No explicit conversion bridge to/from `num`/`numw`/`bignum` (e.g. an explicit "round this num to an int" operator) — right now a fractional value can never reach an `int` at all by design, but there's also no sanctioned way to deliberately truncate/round a `num` into one either; would need its own design decision (truncate? round? crash on a fractional source?) if ever wanted.
- An `int` expression made entirely of literals (`(5000000000) x (5000000000)`, or a single out-of-range literal like `(200) [precision:8]`) that overflows is now caught at compile time instead of only crashing at runtime. Deliberately narrow: no constant propagation through variables (even ones assigned from a literal), no compile-time catch for division-by-a-literal-zero or a negative literal `xx` exponent (different, narrower failure modes than overflow), and `xxx` isn't constant-folded at all. Any of these could be extended later using the same `try_const_eval_int`/`ConstInt` machinery in typecheck.rs, but each would be its own design/scope decision, not an automatic given.

## Known implementation gaps

- `str` now has runtime construction via `stch` and real memory management (every `str` in a variable is its own `strdup`'d copy, freed at scope exit/reassignment/return, mirroring `bignum`). ~~One remaining inefficiency: a `str` value stored somewhere always got its own fresh copy even when the source was already an unshared temporary (a `stch` result, a str-returning call) — a redundant extra `strdup` in that case~~ -- fixed: `compile_and_coerce` now adopts a not-yet-consumed `str_temps` entry directly (the identical check `bignum`'s own adoption already does, simpler here since a `str`/`file` value has no precision to match, just the raw pointer), skipping the `strdup` entirely whenever the source is genuinely an unshared temporary. Measured ~1.21x faster on a loop repeatedly building and storing a `stch` result -- smaller than any of `bignum`'s wins, since a `strdup` on a short string is far cheaper than a GMP allocation, but still real. Verified correct against the existing `stch.cyborgpl` example (concatenation, auto-conversion, a function returning a `stch` result, a looped accumulator -- all unchanged output) and no leak/double-free across 2,000,000 repeated calls to a function returning a fresh `stch` result (identical peak memory footprint vs. 50 calls).
- Correction to the `99411f8` commit message's performance claim: it stated "roughly 4x wall-clock" for the bignum copy-skip optimization above. Re-measured later with a controlled 3-checkout before/after/after-both (2,000,000-iteration `acc = acc + (1)` loop, 3 runs each, release build): the real speedup is ~1.45x (~0.219s before -> ~0.151s after), not 4x. The subsequent precision-widening commit (`be9b1e2`) has no measurable performance effect of its own, as expected (it only changes which precision a result is constructed at, computed statically at compile time). The optimization itself is real and correctly implemented — only the specific "4x" figure in that old commit message was wrong/unverified and shouldn't be trusted as a comparison point going forward.
- ~~Intermediate bignum binary-op results always compute at the default precision (256 bits) regardless of operand precision~~ -- fixed: intermediate results now widen to the larger of the two operands' own precisions (mirroring `num`'s "widen to the larger operand" behavior), computed via static AST inspection (`bignum_precision_of_expr` in codegen.rs) rather than a runtime GMP query, since a bignum's precision is fixed at construction and never changes afterward. Negation preserves the operand's own precision the same way; factorial still deliberately forces the default regardless of operand precision (unchanged, matching `num`/`int`'s own factorial convention).
- ~~A bare literal combined with a bignum inside a `while` loop (e.g. `acc + (1)`) got a fresh `bignum_new` + `set_d` (a real GMP malloc) on every single iteration~~ -- fixed: `Stmt::While`'s codegen now scans its own condition and body (via `find_hoistable_bignum_literals`/`scan_expr_for_bignum_literals`, recursing into `if` branches but never into a nested loop's own condition/body -- that loop hoists independently, to its own preheader) and constructs each such literal once, right before the loop, reusing it every iteration afterward (`compile_hoisted_or_literal`). Scoped exactly like a block's own local variables -- a dedicated `scopes` frame pushed before the loop and popped (with frees) once it's done -- so an early `return` from inside the loop still frees it correctly via the existing "free every open scope" pass `Stmt::Return` already has. Measured ~1.68x faster on the same tight accumulation loop the `99411f8`/`be9b1e2` benchmarks above used; verified correct across nested loops, `if` branches inside a loop, early return from inside a loop, and the same literal value used both inside and outside a loop in one function, with peak memory footprint identical whether the enclosing function is called 50 times or 2,000,000 times (no leak, no double-free). Deliberately narrow: only the exact literal-paired-with-bignum `Binary` shape `compile_expr` already special-cases -- not general loop-invariant code motion for arbitrary bignum subexpressions (e.g. `acc + (some_var x (2))` where the right side never changes across iterations isn't hoisted, even though it's just as invariant).
- ~~A chained `+`/`-` bignum expression (`a + b + c + d`, compiled bottom-up as nested `Binary` nodes) allocated a fresh handle for every intermediate step, even though each one is immediately superseded by the next~~ -- fixed: whenever the left operand of a chained `Add`/`Sub` is itself a not-yet-consumed `bignum_temps` entry (the same "nothing else references it" check `compile_and_coerce`'s adoption already uses) at exactly the op's own result precision, the op now accumulates directly into that existing handle (GMP documents that `mpf_add`/`mpf_sub`'s destination may alias a source operand) instead of allocating a new one. Profiled first with a standalone GMP microbenchmark (not a guess) before implementing: ~1.8x for a single extra chained term, ~2.5-2.8x for a 4-op chain -- confirmed matching in the real compiler afterward. Verified correct for mixed `+`/`-` chains, the same operand appearing twice in one chain, a chain that widens partway through (correctly falls back to a fresh allocation when the running precision doesn't match, rather than corrupting a too-narrow buffer), a chain result feeding into a further op, high-precision propagation through a fully-fused chain (a repeating-decimal check, not just small integers), and no leak/double-free across 2,000,000 repeated calls to a function containing a chain (identical peak memory footprint vs. 50 calls). Extended the same day to `Mul`/`Div` too, after separately profiling and verifying GMP's aliasing guarantee for `mpf_mul`/`mpf_div` specifically: `Mul` gets a similar win to `Add`/`Sub` (~2.2-2.6x on a 4-op chain), `Div` a smaller but still real one (~1.45x measured in the real compiler -- division's own cost dominates more, so the allocation removed is a smaller slice of the total). `Pow` was profiled too and *initially excluded*: `xx` parses right-associative (`parse_power` in parser.rs recurses into its own right side), so a genuine `a xx b xx c` chain builds with the reusable intermediate on the *right* -- a side the left-operand-only check doesn't inspect. The original Pow microbenchmark wrongly assumed the same left-associative shape the other four ops have; a real `xx` chain measured *no* improvement once actually tested end-to-end in the compiler, which is what caught the mistake before it shipped as a misleading no-op inclusion.
- ~~Following up the same day, after being asked "what about `xx`/`xxx`" specifically: a genuine right-associative `a xx b xx c` chain's reusable intermediate really does sit on the right, and reusing it turned out both safe and worthwhile once actually checked (not assumed)~~ -- fixed: verified `bignum_pow`'s own shim fully reads and converts its exponent argument to a plain integer *before* touching its destination, so `dst` aliasing `exp` (not just `dst` aliasing the first argument, the case already relied on for `Add`/`Sub`/`Mul`/`Div`) is safe -- confirmed with a standalone correctness check, then profiled (~1.4-1.7x standalone, ~1.28x measured for real in the compiler once system noise from a concurrent build was ruled out). The dispatch now checks the right operand specifically for `Pow` (only when the left check didn't already match), reusing that handle as the destination when found. **A real, previously-unreachable correctness bug was caught and fixed along the way**: `bignum_pow`'s own negative-exponent branch (`if (mpf_sgn(e) < 0)`) re-read its exponent pointer *after* `mpf_pow_ui` had already written the result into `dst` -- harmless before this round, since `dst` was always a fresh handle distinct from `exp`, but wrong the moment `dst` can alias `exp`: reading a stale (freshly-overwritten) value's sign instead of the original exponent's. Confirmed broken with the old shim (`2 xx (-2 xx 1)` gave `4` instead of the correct `0.25`) and fixed by capturing the sign into a local variable before `mpf_pow_ui` runs. `xxx` (tetration) chains would need real new plumbing (bignum tetration doesn't use the generic dispatch), but its *own internal computation loop* (used by a single `xxx`, not a chain) had the identical fresh-alloc-per-iteration pattern -- fixed the same way (one handle reused via the same dst-aliases-exp trick, verified safe above), simplifying the loop to no longer need a store/load slot at all since the handle's own pointer never changes across iterations. Measured ~1.64x faster on a real `xxx` call in a loop, even at a modest tower height of 4. Verified correct for a real `xx` chain, the same chain evaluated twice, a 4-term `xx` chain, precision widening on the exponent side, the negative-exponent-plus-aliasing case specifically, and `xxx` still producing correct values (`2 xxx 4 = 65536`, `3 xxx 3 = 7625597484987`) after its internal rewrite -- plus no leak across 2,000,000 repeated calls to functions containing each kind of chain.
- ~~Every `bignum` construction cost two separate heap allocations (the handle itself, plus GMP's own internal digit-storage buffer inside `mpf_init2`), hit fresh every time regardless of how many times an equally-sized handle had already been allocated and freed before~~ -- fixed (originally): `runtime/gmp/bignum_shim.c` installed a size-bucketed freelist pool via `mp_set_memory_functions`. Profiled standalone before implementing (a tight construct/use/free cycle landed within ~1-2x of the *theoretical floor* of doing no allocation at all, ~5-8x faster than plain malloc/free) and confirmed for real in the compiler (~2.5x on an end-to-end workload). ~~The one real behavior change from plain malloc/free: a pooled block was never returned to the OS once freed, only kept for reuse -- fine for a short, run-to-completion script, but a real problem the moment a longer-running construct (a timer, an event loop) exists -- a brief burst of many live `bignum`s would keep that peak memory reserved for the rest of the process's life~~ -- **replaced the same day**: the hand-rolled pool is gone; GMP's allocator hook now points directly at [mimalloc](https://github.com/microsoft/mimalloc)'s own `mi_malloc`/`mi_realloc`/`mi_free` instead. Neither Rust nor GMP solve this "give memory back after a while" problem themselves (both just delegate to the system allocator by default) -- mimalloc provides *decay-based* reclamation (cache freed memory for reuse the same way a hand-rolled pool would, but automatically release it back to the OS once it's gone unused for a while), the same well-proven fix real-world long-running Rust services reach for when the platform default doesn't give memory back well enough (e.g. TiKV's `tikv-jemallocator`). Requires `brew install mimalloc` (added to `build.rs`/`main.rs`'s link step, mirroring the existing GMP-via-Homebrew pattern exactly). Verified: every existing bignum test/benchmark from this session's earlier rounds re-confirmed correct (chains, precision widening, multiple simultaneous precisions, tetration, negative-exponent aliasing), comparable performance to the hand-rolled pool (~2.5x still holds on the same end-to-end benchmark), and peak memory footprint still flat between 50 and 2,000,000 repeated allocations (mimalloc's own baseline overhead is somewhat higher than the trivial hand-rolled freelist, but bounded the same way, not growing with total allocations). Full example-suite regression pass.
- `mem2reg` now runs before object-file emission (promotes alloca/store/load into plain SSA values wherever safe). Nothing beyond it yet — inlining, dead code elimination, constant folding across function boundaries, etc. are all still deliberately deprioritized.
- The new type checker (`src/typecheck.rs`) only checks *shape* compatibility, not value validity — e.g. `var:bignum 'x' = (ref:var:str 'y');` type-checks fine (`str` is a valid bignum source, for numeric-literal text like `"3.14"`), but if `'y'` holds actual non-numeric text, that's still only caught at runtime (or not caught at all -- `bignum_set_str` on garbage input is undefined). Deliberately out of scope for a checker that mirrors codegen's existing coercion rules rather than adding new restrictions.
- `input:str 'x';` (stdin) strips the trailing newline; `input:str 'x' [from*(dest)*];` (a file) does not -- it hands back the file's exact, complete content. Not a bug (the file-source case was deliberately defined as "whole content, unmodified"), but worth knowing since it means a file written by `overwrite`/`print [to*...*]` (which always appends a newline) will read back with that newline still attached.
- Found while stress-testing arrays: any `build_alloca` placed inside a hand-built runtime loop's body block (as opposed to the function's entry block) is a genuine dynamic stack allocation on every iteration, since LLVM only reclaims it when the function returns — enough iterations (well under a million) segfaults the compiled program. Fixed for all the array codegen helpers via a new `entry_alloca` (see `AGENTS.md`); the same latent bug in `compile_tetration`/`compile_bignum_tetration`/`compile_factorial`/`compile_bignum_factorial` (pre-existing, unrelated to arrays) has since also been fixed the same way. ~~Still unaudited: `Stmt::VarDecl`/`Stmt::Input`/`Stmt::Clock`'s own variable-slot allocas aren't hoisted either — harmless in every example so far (they always declare once outside a loop and reassign inside it), but a `var:` declaration written directly inside a `while` body, re-declaring each iteration, would hit the same bug~~ -- fixed: all three now use `entry_alloca` instead of a plain `build_alloca`. Confirmed this was a real, reachable crash (not just theoretical) by testing the exact scenario before and after: a `var:num` declared directly inside a 5,000,000-iteration `while` body segfaulted (`exit code: None`, killed by signal) with the old code, and computes the correct sum with the fix. `clock:num` declared the same way inside a 3,000,000-iteration loop verified working too.
- `int`'s literal grammar can't write the exact value `i64::MIN` (`-9223372036854775808`) directly -- its positive form (`9223372036854775808`) already exceeds `i64::MAX` on its own, before the negation that would produce it is even applied (the same `INT_MIN`-as-a-literal quirk most C-like languages have). Reachable via arithmetic instead (`-(9223372036854775807) - (1)`); every *other* literal in the full `i64` range parses exactly (parsed from the literal's original digit text, not the lexer's lossy `f64`, mirroring the fix `bignum`'s bare literals already needed).
- ~~A bare `return;` (no value) written directly inside `START...END` built `ret void` in the generated `main`, even though `main`'s real LLVM signature is always `i32` (the C runtime's own convention) -- left `main`'s return-value register unset, so the process exited with an undefined, garbage code instead of the intended `0`~~ -- fixed: a new `in_entry` flag (set only while compiling `START...END`) makes `Stmt::Return`'s no-value case build `ret i32 0` there specifically, matching the `ret i32 0` `compile_entry` already builds for simply falling off the end without an explicit `return`. A genuine void-returning user function (one with no `-> type` at all) is unaffected -- its own bare `return;` still builds a real `ret void`, since `in_entry` is only ever true while compiling the entry point. Found while explaining `START...END`'s design to the project author and confirmed with a live before/after test: the exact reproduction (`print`, then a bare `return;`, then a second `print` that should never run) exited with code `14` (meaningless garbage) before the fix, `0` after -- the early-exit control flow itself was always correct, only the leftover exit code was ever wrong.
